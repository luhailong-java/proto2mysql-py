# 缓存：为什么条目要带一个头部

> 只有打算调 `db.enable_cache(...)` 时才需要读这篇。

## 一、这个缓存是干什么的

标准的 cache-aside（旁路缓存）：

```
读：先查缓存 → 没有就读 MySQL → 把结果写回缓存
写：先写 MySQL → 成功后删掉缓存里那条
```

缓存里存的是**整条记录序列化成 protobuf 之后的字节**，
key 是 `pb:<表名>:<主键值...>`，比如 `pb:player:10086`。

库本身不依赖任何 Redis 客户端——你注入一个实现了 `get/set/delete` 的对象就行。
**任何缓存错误都不影响数据库操作，只会降级为直读 DB。**

## 二、一个非常隐蔽的事故（已修复）

### 先看现象

滚动发布期间，运维发现：

- 玩家反馈某个新加的字段"有时候有值、有时候是 0"
- 去 MySQL 里查，**数据完全正常**
- 日志里**一条错误都没有**
- 重现不了——刷新几次就好了，过一会儿又出现

### 根因

关键在于一句话：

> **缓存里的那条记录，是"按列从 MySQL 读出来、再一列一列填进 message"的，
> 不是从 protobuf 字节解析出来的。**

这句话为什么要紧？因为 protobuf 有一个著名的特性叫 **unknown fields**：
用旧版本的 message 去解析新版本写的字节时，它不认识的字段会被**原样保留**，
再序列化出去时还在。很多人（包括我）第一反应会觉得"protobuf 天然向前兼容，
所以缓存没问题"。

**但那个保护在这里完全不适用。** v1 的 message 里根本没有 `foo` 这个字段——
它不是从字节里解析来的，是 v1 自己发的 `SELECT id, name, gold`
（注意：**没有 foo**）读回来一列一列填的。所以它写进缓存的，
是一条**结构上就残缺**的记录。

完整的时序：

```
1. v2 加了新字段 foo，DB 里 player#10086 的 foo = 42

2. v1 的某个实例读这条记录
   → 缓存未命中
   → 它发的是 SELECT `id`, `name`, `gold` FROM player  ← 它不知道有 foo
   → 得到一条 foo 缺失的 message
   → 序列化，写进共享的 Redis：key = pb:player:10086

3. v2 读同一条记录
   → 缓存命中！
   → 解析出来 foo = 0
   → 而 MySQL 里 foo 明明是 42                          ← 事故

4. v2 写了一次 → 它只 delete key
5. v1 下次读 → 又投毒一次 → 循环
```

**这就是"值随机闪烁"的来源**：取决于最近一次是谁把缓存填上的。
而且因为缓存是弱依赖（出错只打 warning），全程零异常、零错误日志，
MySQL 里的数据自始至终是对的——**只能靠对账发现**。

## 三、修法：把"写入方认识哪些字段"记进缓存值

### 走过的弯路：把版本拼进 key（❌ 更糟）

第一直觉是给 key 加一个 schema 指纹：

```
v1 写 → pb:player:<指纹A>:10086
v2 写 → pb:player:<指纹B>:10086
```

两个版本天然不共享条目，投毒路径直接消失。看起来完美。

**但这会让缓存失效彻底失灵。** 因为"删缓存"和"读缓存"用的是**同一个 key 生成器**：

```
v2 读 → 缓存写到 pb:player:B:10086
v1 写库 → 它去删 pb:player:A:10086      ← 自己那个指纹
v2 那条 pb:player:B:10086 永远没人删     ← 一直脏到 TTL 到期
```

**这把「读到残缺数据」升级成了「跨版本永久脏读」，比原来的问题更严重。**

### 正解：指纹进 value 的头部

key 一个字不改，改的是**存进去的内容**：

```
┌────────┬─────────┬────────┬──────────────┬─────────────────┐
│ "P2MC" │  0x01   │ count  │ 字段号(升序)  │  protobuf 字节   │
│  4B    │  1B版本 │ varint │ count个varint │     剩余全部     │
└────────┴─────────┴────────┴──────────────┴─────────────────┘
```

前面那一小段记的是「**写这条缓存的进程，认识哪些字段**」。

读的时候做一次**超集判定**：

> 写入方的字段集 ⊇ 我的字段集 → 采用；否则当未命中，回源查库。

| 谁读谁写的 | 判定 | 结果 |
|---|---|---|
| v1 读 v2 写的 | v2 认识得更多，是超集 | ✅ 采用（多出来的字段对 v1 就是 unknown fields，无害） |
| v2 读 v1 写的 | v1 认识得更少，不是超集 | ❌ 当未命中，回源查库 |
| 老版本写的裸 pb 字节（没有 `P2MC` 头） | 认不出来 | ❌ 当未命中，下次写会原地覆盖成新格式 |

**miss 是单向的**——只有"认识更多字段的一方"会 miss。
所以滚动发布期间的缓存雪崩面比"换 key"小得多，而且是**原地覆写**，
不会像换 key 那样把旧 key 空间搁浅在内存里。

### 两个语言逐字节一致

Go 版和 Python 版产出的信封字节完全相同，所以两边可以**共用同一个 Redis**。
字段号必须**升序**写入，保证同一个集合永远产出同一份字节。

## 四、顺手修掉的另一个洞：解析失败会清空主键

原来的读路径是这样的：

```python
message.Clear()                      # ← 先清空
message.ParseFromString(data)        # ← 再解析
```

如果解析失败（缓存里的字节坏了、被别的程序写过、编码不对），
异常抛出时**调用方 message 的主键已经被清成 0 了**。

而 `find_one_by_pk(out)` 的 `out` **既是入参也是出参**——
你传 `Player(id=10086)` 进去，它拿 `id` 去查库、再把结果填回同一个对象。
主键一被清空，上层就拿着 `id=0` 回去查库，于是查错行 / 查不到，
而且**完全看不出根因**。

现在改成：解析到一个临时对象，成功了才拷回调用方的 message。

## 五、用缓存的注意事项

**必须设一个有限的 TTL。**

```python
db.enable_cache(my_redis_cache, ttl=300)   # ✅
db.enable_cache(my_redis_cache)            # ⚠️ 不过期
```

理由：库只在按主键的单行读写上做缓存失效。按 `WHERE` 条件的批量更新/删除
（`update_where` / `delete_where`）**无法定位受影响的主键，不会失效缓存**。
TTL 是这类情况唯一的兜底。

需要手动失效时：

```python
db.invalidate_cache(msg1, msg2, ...)
```

**别用 `DictCache` 跑多副本服务。** 它是进程内字典，只用于测试和单进程小工具；
多副本用它，各个副本会读到互相看不见的旧值。
