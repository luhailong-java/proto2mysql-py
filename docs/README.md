# proto2mysql 文档

这个目录讲的是**用这个库的时候会踩到什么坑，以及为什么**。

如果你只是想知道怎么调用，看仓库根目录的 [`README.md`](../README.md)。
这里回答的是另一类问题：「为什么我加了个字段，线上数据就没了？」

## 先读这一段（30 秒）

这个库会**自动帮你改线上表结构**。这个能力很方便，但它有一个前提假设：

> **同一时刻，只有一个版本的程序在跑。**

一旦你开始做**滚动发布 / 金丝雀发布**（新旧两个版本的进程同时在线），
这个假设就不成立了，而库本身**没有 schema 版本的概念**——
每个进程都把「我自己 .proto 里写的那份结构」当成唯一正确的目标，
然后想方设法把线上表拉成那个样子。

新旧两个版本互相拉扯的结果，就是本文档要讲的一系列事故。

**所以最重要的一条规矩是：**

| 你的部署方式 | 该怎么用 |
|---|---|
| 单进程 / 停机更新（同一时刻只有一个版本） | 默认配置就行，什么都不用改 |
| **滚动 / 金丝雀发布（新旧版本同时在线）** | **必须打开 `expand_only`**，见 [schema-evolution.md](schema-evolution.md) |

## 名词表（本文档全篇通用）

看不懂后面的文档时回来查这里。

| 名词 | 意思 |
|---|---|
| **DDL** | 改**表结构**的 SQL：`CREATE TABLE` / `ALTER TABLE` / `DROP TABLE`。与之相对的 DML 是改**数据**的 SQL（INSERT/UPDATE/DELETE）。 |
| **滚动发布 / 金丝雀发布** | 更新服务时不一次性全换，而是先换一部分实例。好处是出问题能快速回滚，代价是**新旧两个版本会同时在线一段时间**。 |
| **v1 / v2** | 本文档里 v1 = 旧版本的程序，v2 = 新版本的程序。 |
| **字段号（pb:N）** | .proto 里每个字段后面的那个数字，如 `string ip = 2;` 里的 `2`。它是这个字段的**身份证**，改名字不影响它。本库把它写进 MySQL 的列注释（`COMMENT 'pb:2'`），迁移时靠它认列。 |
| **收窄 / 拓宽** | 收窄 = 把列改成装得更少的类型（`bigint`→`int`、`mediumtext`→`varchar(255)`），会丢数据。拓宽反之。 |
| **expand（扩展） / contract（收缩）** | 只加不减的变更叫 expand（加列、加索引）；删列、改类型、加约束叫 contract。滚动发布下只有 expand 是安全的。 |
| **ODKU** | `INSERT ... ON DUPLICATE KEY UPDATE` 的缩写。「有则更新、无则插入」，且**只更新你点名的列**。 |
| **REPLACE INTO** | MySQL 的另一种"有则更新"写法，但它实际是**先 DELETE 再 INSERT**——语句里没提到的列会回到默认值。危险。 |
| **information_schema** | MySQL 自带的一个特殊库，里面记着「有哪些表、每张表有哪些列、什么类型、什么注释」。本库靠读它来对比线上结构与 .proto。 |
| **fail-fast / fail-closed** | 出问题时立刻报错停下，而不是继续跑。反义是"静默降级"——继续跑但结果是错的，那种最难排查。 |

## 本库的两条设计立场

理解这两条，后面很多行为就不用死记了。

**一、永不破坏数据。**

- 从不 `DROP COLUMN`：.proto 里删掉字段，线上那列**原封不动留着**（变成没人写的"孤儿列"）。
- 从不收窄类型：线上比目标宽的列一律不动。
- 需要真的删列/收窄？请人工写 `ALTER`，库不替你做这个决定。

**二、宁可吵，不要静。**

能在启动时报错的，绝不拖到第一次写入才报；
能打一条告警的，绝不无声无息。因为这类库最可怕的失败模式不是"报错了"，
而是**"没报错，但数据悄悄错了"**——那种问题往往几周后才由对账发现。
