# 2026-08 缺陷修复全记录

这一轮针对「滚动 / 金丝雀发布」场景做了一次完整审查，
在 Go 与 Python 两个实现里找到 **16 条缺陷**并全部修复。
（第 14 条是第一次拿**真 TiDB** 跑集成测试时发现的；
第 15、16 条来自对抗复核，是我在收尾自查时才闭环的。）

**共同点：它们几乎全部是"不报错、只静默出错"的类型。**
不是崩溃、不是异常，而是数据悄悄变了、查询悄悄变慢、结构悄悄没生效——
往往几周后由对账或线上投诉才发现。

> 两个实现（Go 版 `luyuancpp/proto2mysql` 与本 Python 版）的所有改动都是
> **对称落地**的，生成的 SQL 保持逐字节一致。

## 1. 自动同步会收窄列类型（P0）

### 现象

滚动发布时，某个字段从 `uint32` 拓宽成 `uint64` 之后，超过 42 亿的值被截断。
过一会儿又好了，再过一会儿又坏——**跟着 pod 重启的节奏**。

### 时序

```
v2 启动 → MODIFY COLUMN `port` bigint unsigned    ✅ 拓宽
v1 某个实例重启 → MODIFY COLUMN `port` int unsigned  ❌ 收窄回去
```

**v1 什么数据都没写，它只是重启了一下。**

### 根因

判断"线上列类型和 proto 要的类型兼不兼容"的函数里，
`int` 和 `bigint` 是**两个不同的基础类型**，在比较基础类型那一步就直接判"不兼容"了，
于是**两个方向都会 ALTER**——完全没有"谁更宽"的概念。

文本族同理：`mediumtext` vs `varchar(255)` 也是不同的基础类型。

> 这条在真实项目里发生过：某个库的 `nickname` 从 `MEDIUMTEXT` 被另一侧按
> `varchar(255)` 重建，结果同一个玩家的同一次改名，**落到宽列副本就成功、
> 落到窄列副本就报 Error 1406**，且不可复现——取决于请求打到哪台机器。

### 改法

给四类「同族类型」加容量阶梯，判定口径统一成**「线上装得下目标就不动它」**：

```
整数    tinyint < smallint < mediumint < int < bigint
文本    char < varchar < tinytext < text < mediumtext < longtext
二进制  binary < varbinary < tinyblob < blob < mediumblob < longblob
浮点    float < double
```

线上 rank ≥ 目标 rank → 兼容，不生成 ALTER；线上更窄 → ALTER 拓宽。

有无符号（`unsigned`）不参与宽窄比较：它决定的是**值域方向**而不是宽窄，
`bigint unsigned` 和 `int` 谁也装不下谁，所以一律 ALTER。

收窄是有损操作，与本库「永不 DROP COLUMN」的立场一致——确实要收窄请人工写 ALTER。

### 怎么验证

`tests/test_migration.py::test_is_type_match_never_narrows`

<a id="2"></a>
## 2. `varchar` / `float` 的长度比较方向是反的（P0）

### 根因

同一个函数里，四个分支的方向**互相矛盾**：

```python
varchar/char:  return target.length >= current.length     # ← 反的
整数:           return current.unsigned == target.unsigned # ← 完全没有方向判断
float/double:  return target.decimal >= current.decimal   # ← 反的
datetime:      return current.length >= target.length     # ← 唯一正确的
```

只有 `datetime` 是对的，而且它有一段注释解释原因——那是上一次真出过事故后修的，
还配了 6 个测试用例。**其余三条从来没人回头看过。**

varchar 那条**两个方向都错**：

| 线上 | proto 要 | 修复前的行为 | 应该 |
|---|---|---|---|
| `varchar(50)` | `varchar(100)` | 判"兼容"→ 不拓宽 → 写 100 字符报 1406 | 要 ALTER 拓宽 |
| `varchar(100)` | `varchar(50)` | 判"不兼容"→ **ALTER 收窄** → 已有数据截断 | 不动 |

### 改法

三条全部与 `datetime` 分支对齐，统一成「线上容量 ≥ 目标容量 → 不动」。

## 3. 改名在滚动发布下乒乓球（P0）

### 现象

改了个字段名，v2 上线后一切正常。过了十分钟，v2 的所有 SQL 突然全部报
`Error 1054 Unknown column`。重启 v2 又好了，过一会儿又坏。

### 时序

```
proto 里 ip(pb:2) 改名成 addr(pb:2)

v2 启动 → CHANGE COLUMN `ip` → `addr`      ✅
v1 重启 → CHANGE COLUMN `addr` → `ip`      ❌ 改回去了
        → v2 立刻 Error 1054
v2 重启 → 又改成 addr → v1 再改回 ip → ...
```

### 根因

库按**字段号**认列（列注释里存着 `pb:2`），看到"有一列注释是 pb:2 但名字对不上"
就生成 `CHANGE COLUMN`。这个逻辑本身是对的、也是本库的招牌特性。

问题在于**库没有 schema 版本的概念**——它无法判断谁新谁旧，
每个进程都把自己的 .proto 当成唯一正确答案。于是两个版本互相改。

### 改法

分两步，**刻意没有把改名关掉**（单进程部署时改名完全正当，是本库最好用的特性之一）：

1. **每次生成 `CHANGE COLUMN` 都打一条 WARNING**，把风险和正确做法写在日志里
2. **新增 `expand_only` 开关（默认关）**：打开后任何非「纯新增」的变更都被拒绝，
   并把具体语句打印出来交人工

```python
db = DB(conn, "mydb", expand_only=True)   # 滚动/金丝雀发布必须打开
```

**为什么 `ADD COLUMN` 可以放行？** 因为库生成的所有 SQL 都按自己 .proto 的字段列
显式列出，从不用 `SELECT *`——所以 v2 加的列对 v1 **完全不可见**，
既不会被读到也不会被覆盖。这是机制保证，不是运气。

### 正确的改名姿势

见 [schema-evolution.md](schema-evolution.md#三业界标准做法expand--migrate--contract)：
加新列 → 双写回填 → 下个版本删旧列，三次发布。

<a id="4"></a>
## 4. 缓存跨版本投毒（P0）

**这是本轮最隐蔽的一条**，完整分析见 [cache.md](cache.md)。

### 一句话

缓存里的记录是**按列从 MySQL 读出来再填进 message 的**，不是从 protobuf 字节解析的，
所以 protobuf 的 unknown-fields 保护在这里**完全不适用**：
旧版本写进缓存的是一条**结构上残缺**的记录，新版本读到就是新字段拿零值——
而 MySQL 里的数据自始至终是对的，**零日志、零异常**。

### 改法

缓存值加一个头部，记「写入方认识哪些字段」，读时做**超集判定**：

```
"P2MC" | 版本 | 字段号个数 | 字段号(升序) | protobuf 字节
```

写入方字段集 ⊇ 读取方字段集 → 采用；否则当未命中回源。
**miss 是单向的**（只有认识更多字段的一方会 miss），雪崩面小。

> **走过的弯路**：第一版把指纹拼进了 **key**。这会让缓存失效彻底失灵——
> 失效路径和读路径共用同一个 key 生成器，v1 写库后删的是自己指纹的 key，
> v2 缓存的那条永远没人删，把「读到残缺数据」升级成「跨版本永久脏读」。
> 已推翻重做。

<a id="5"></a>
## 5. `save` 走 `REPLACE INTO`，抹掉未知列（P0）

### 根因

`REPLACE INTO` 的语义是**先 DELETE 再 INSERT**，语句里没提到的列不是"保持原值"，
而是**回到列默认值**。而列清单来自本进程的 descriptor：

```
v2 写进 foo = 42
v1 执行一次 save()
  → REPLACE INTO player (id, name, gold) VALUES (?, ?, ?)
  → foo 回到 0                                    ← 数据没了，零报错
```

还会触发外键级联删除。

### 一个内部矛盾（Go 侧）

Go 仓库里 `GormDB.Save` 一直用的是 `clause.OnConflict{UpdateAll}`（= ODKU，**保留未知列**），
而 `DB.Save` 用 `REPLACE INTO`（**抹掉未知列**）——**同一个库、同名方法、
相反的数据安全语义**。这也说明"换成 upsert"不是新设计，同仓库里早就有一份跑着的实现。

### 改法

`save` / `batch_save` 改走 `INSERT ... ON DUPLICATE KEY UPDATE col = VALUES(col), ...`，
覆盖本进程认识的**全部**列（零值也写，因为 save 的语义是"整行落库"），
但**不动本进程不认识的列**。

`SQLBuilder.replace` / `batch_replace` 保留为**显式逃生口**，
docstring 里写明了危险，建议 CI 里 grep 拦一道。

> 顺带：这条路径在两个仓库里**原本都是零测试覆盖**，所以改动前后都补了断言。

<a id="6"></a>
## 6. NULL 列导致跨行数据串位（P0）

### 现象

```python
out = KitchenSink(id=1)
db.find_one_by_pk(out)     # alice: payload = b"alice-data", tier = GOLD

out.id = 2
db.find_one_by_pk(out)     # bob 这几列在库里都是 NULL
# → out.payload 还是 b"alice-data"，out.tier 还是 GOLD
# → bob 拿到了 alice 的数据
```

### 根因

「列值为 NULL 时把字段重置成默认值」的函数只处理了 **8 种标量**，
**刻意跳过了 `bytes` / `enum` / `message`**（注释写着"与 Go 版一致"）。
于是这三类字段在 NULL 时被**原样留着**，串到下一行。

而 `find_one_by_pk(out)` 的 `out` **既是入参（主键）又是出参**，
复用同一个 message 正是这个 API 的天然用法——**这不是误用**。

### 改法

`bytes` / `enum` 补进重置列表（都能直接赋默认值）；
`message` 单独走 `ClearField`（子消息没有可赋的默认值）。

### 怎么验证

`tests/test_pbconv.py::test_null_columns_do_not_leak_across_rows`

<a id="7"></a>
## 7. `GormDB` 完全没有 ALTER 路径（P0，Go 独有）

`GormDB.CreateOrUpdateTable` 只执行 `CREATE TABLE IF NOT EXISTS`，
整个 949 行的 GormDB **一条 ALTER 都没有**。

在一张已经存在的表上，它是**无条件、每次、永久**的 no-op。
注意这不是第 8 条那种"并发下才触发"的竞态，而是**百分之百不生效**：
proto 里加了字段，进程照常启动、零日志零错误，
一直到第一条 SELECT 才报 `Error 1054`，而且**重启也不会好**。

用 GormDB 的人以为自己有自动建表能力，实际上只有"第一次建表"能力。

**改法**：与 `DB.syncTableSchema` 走同一套逻辑（建表 → 读 information_schema →
生成 ALTER → 落地），并同样支持 `ExpandOnly`。

## 8. 建表分支提前 return，新列从未被加（P1）

### 根因

```python
if not self.is_table_exists(table.table_name):
    self.execute(table.get_create_table_sql())   # CREATE TABLE IF NOT EXISTS
    self._table_exists_cache[table.table_name] = True
    return                                        # ← 直接 return
```

空库上两个版本同时冷启动：

```
v1 检查 → 表不存在 → CREATE（3 列）
v2 检查 → 表不存在（它检查的那一刻确实还不存在）
v2 CREATE TABLE IF NOT EXISTS → 只拿到一条 Warning 1050，不报错、不改结构
v2 return → 它的新列从未被添加
```

**v2 启动成功、零异常**，一直到第一条 SELECT 才报 `Error 1054`，
而且表存在性缓存已置 True，**重启也不重新对齐，不自愈**。

### 改法

建完**不 return**，继续走列对齐。读元信息是直连 `information_schema`（不走缓存），
拿到的是真实建成的结构，缺什么补什么。自己建成功的那条路径上对齐结果为空，
只多一次查询，代价可忽略。

## 9. 字段号复用 → 隐式类型转换吃掉整列（P1）

见 [schema-evolution.md 场景 3](schema-evolution.md#场景-3字段号复用数据被隐式类型转换吃掉已修复)。

**改法**：改名分支加一道类型闸——旧列类型与新字段类型**跨族**时直接报
`FieldNumberReusedError`，不生成 `CHANGE COLUMN`。

这条**没有开关**，因为字段号复用没有任何正当用途。

<a id="10"></a>
## 10. 改名目标列的选择每次运行都可能不同（P1，Go 独有）

Go 版构建「字段号 → 列名」映射时是边遍历 map 边写的，
而 **Go 的 map 迭代顺序是随机化的**。

正常情况下一个 `pb:N` 只对应一列，看不出问题。但线上表出现两列带同一个 `pb:N` 时
（DBA 照 `SHOW CREATE TABLE` 复制一个备份列就会），
**每次运行挑中的列都可能不同**，产出的 `CHANGE COLUMN` 也就不同——
其中一种会去改那个备份列。

**同一个库、同一份 proto、同一个线上结构，跑两次得到两份 DDL。**
Python 侧是确定性的 dict 推导，所以只有 Go 有这个问题。

**改法**：冲突时取**列名字典序最小**的那个（规则简单、可复现），
同时打一条告警——重复的 `pb:N` 本身就是个需要人工处理的异常。

<a id="11"></a>
## 11. 结构同步零并发保护（P2）

全库没有任何咨询锁。N 个副本同时冷启动 → 一个 ALTER 成功、
其余全部撞 `Error 1060 Duplicate column name` → 启动失败。

**下一次重启会成功**（列已经存在，对齐结果为空），所以它是**"自愈式蒙对"**——
日志里留下一串启动失败、服务最终起来了，很容易被当成偶发 flake 忽略，
直到某次重启风暴把它放大。

### 改法

`sync_all_tables()` 全程持一把 MySQL 咨询锁（`GET_LOCK`）。

**拿不到锁不阻断**：`GET_LOCK` 超时返回 0、连接异常返回 NULL，
而 TiDB 等兼容实现不一定支持这个函数。所以拿不到只降级为
「无锁执行 + 一条告警」——把可用性看得比"锁一定要拿到"更重：
拿不到锁最坏是撞 1060、重启自愈；因为拿不到锁就拒绝启动，
是把一个并发问题升级成可用性事故。

Go 侧顺带把遍历表的顺序也排序了（map 迭代随机化会让多副本以不同顺序抢元数据锁，
且失败时"改到第几张表"每次都不一样，排障对不上）。

<a id="12"></a>
## 12. 已有表的索引永远不会被补（P2）

索引只出现在 `CREATE TABLE` 分支。**表一旦建成，之后在 .proto 里新加
`index` / `unique_key` 完全不生效**，而且零提示——查询照常能跑，
只是走全表扫描，数据量上来才表现为"莫名其妙变慢"，
谁也想不到是建表选项没落地。

### 改法

同步结构时读 `information_schema.STATISTICS`，补上缺失的索引。

**只加不删**：线上多出来的索引一律不动（可能是 DBA 按查询模式手工加的，
库没有立场去删）。索引名与 `CREATE TABLE` 分支保持一致，
否则同一份 proto 在"新建表"和"老表补索引"两条路径上会产出不同的索引名。

⚠️ 补 `UNIQUE KEY` 时线上若已有重复行，这条 ALTER 会失败——
这是预期的 fail-closed 行为，需先人工去重再重试。

<a id="13"></a>
## 13. TiDB 的异步 DDL 零等待（P2）

**TiDB 的 DDL 是异步 online 的**：`ALTER` 语句返回时，schema 变更只是进了 DDL 队列，
各个 TiDB 节点要按 lease（默认 45s）分批加载新的 schema 版本。

而库执行完 ALTER 立刻清缓存、按新 proto 发 INSERT/SELECT。
这段窗口里连到**还没加载新 schema 的节点**就会报 `Unknown column`——
启动日志漂亮，第一批请求全挂。

### 改法

ALTER 之后**回读 `information_schema` 直到本次新增的列真的可见**，最长等 60 秒。

两个刻意的设计：

- **不去检测"后端是不是 TiDB"**：版本号/变量嗅探很容易被兼容层骗过，
  而"回读直到结构真的对上"是纯行为判定，对 MySQL、TiDB、任何兼容实现都成立。
  MySQL 单机上这一步立刻就过，几乎零开销。
- **超时只告警不报错**：结构可能确实还在后台排队，报错会把"慢"升级成"起不来"。

只等**本次新增的列**（MODIFY / CHANGE 改的是已有列，回读时本来就看得见）；
一列都读不到时立即放弃（真表不可能零列，那是权限/库名的问题，继续轮询只会白等）。

<a id="14"></a>
## 14. TiDB 上补主键会把列对齐一起带崩（P0，2026-08-26 真库实测发现）

### 怎么发现的

**第一次拿真 TiDB v8.5.1 跑集成测试就撞上了。** 6 个测试同时失败，
但根因只有**一个**——其余 5 个全是连带崩塌。

### 根因

补主键那条路径**刻意**把 `MODIFY COLUMN id ... AUTO_INCREMENT` 与 `ADD PRIMARY KEY`
放进同一条 ALTER（绕开 MySQL 的 Error 1075「自增列必须是键」），
而那条 ALTER 里还夹着**本次全部的 ADD COLUMN**，理由写在注释里是
"同一条 ALTER 保证列对齐与补主键原子成功或失败"。

问题是 **TiDB 根本不支持给已存在的列加 AUTO_INCREMENT**：

```
Error 8200 (HY000): Unsupported modify column: can't set auto_increment
```

实测过合并一条和拆成两条，**都一样**——这是 TiDB 的硬限制，不是语句写法问题。
于是整条 ALTER 原子失败，**所有 ADD COLUMN 一起废掉**：

```
服务启动成功、零异常
→ 第一条 SELECT 就 Error 1054 Unknown column 'ip'
→ 而根因埋在一条看起来只是"补主键"的语句里
```

### 改法

**把补主键拆成独立的第二条 ALTER**：

```
ALTER #1：列对齐 + 索引补齐          ← 服务能不能跑，全看这条
ALTER #2：MODIFY(auto_inc) + ADD PRIMARY KEY
```

主键列自己的那条 MODIFY 要**挪到第二条里**，否则留在第一条会因为
"自增列还不是键"撞 MySQL 的 Error 1075。

这样 TiDB 上第二条仍然会失败，但**列已经对齐好了，服务能正常跑**，
运维再单独处理主键。那点"原子性"换来的代价远大于收益。

错误信息也改成直接点名两个可能：

```
表 golang_test 的列已对齐，但补齐主键失败: Error 8200 ...
  两个常见原因：
    1) 线上已有重复行——先人工去重再重试
    2) 后端是 TiDB——它不支持给已存在的列加 AUTO_INCREMENT（Error 8200）
```

### 效果

| | 修复前 | 修复后 |
|---|---|---|
| MySQL 8.4 | 全绿 | 全绿 |
| TiDB v8.5.1 | **6 个失败**，列没加上 | 1 个失败（已按后端跳过），**列正常对齐** |

### 给用户的含义

**表已经上线且没有主键时，在 TiDB 上永远补不上自增主键。**
只能重建表，或去掉 `auto_increment_key` 改用别的主键生成方式（如雪花 ID）。
详见 [testing.md](testing.md#三tidb-的能力边界)。

<a id="15"></a>
## 15. schema.sql 的文件级顺序两边不一致（P1）

### 根因

`WriteCreateTableSQL` 两边的**排序键不同**：

| | 排序键 |
|---|---|
| Go | 注册键（proto full name） |
| Python | `table_name` |

**没声明 `table_name` 选项时两者恰好相同**，所以这个分叉长期看不出来。
一旦用了 `WithTableName`（比如 proto 叫 `game.v1.PlayerData`、表叫 `player_data`），
同一批 CREATE TABLE 会以**不同顺序**落进 `schema.sql`——逐字节就不一致了。

而现有的 golden 测试是**逐表断言**的，盖不到文件级顺序，所以它一直绿着。

### 改法

Go 改成按 `table_name` 排。`table_name` 才是真正出现在 SQL 里的东西，
也是人看 `schema.sql` 时用来找表的东西。

**同时给跨语言对拍加了一条用例**（`ddl/schema_file/multi_table_order`）：
两张表，注册键顺序与表名顺序**故意相反**。这条分叉再也回不来了。

<a id="16"></a>
## 16. 收窄被抑制时完全静默（P2）

### 现象

有人在 `.proto` 里把 `uint64` 改回 `uint32`，期待线上那列跟着变窄。
重启服务，**什么也没发生**——列还是 `bigint unsigned`，日志里一个字都没有。

### 根因

第 1 条修复引入的"永不收窄"是对的，但它成了本库**唯一一个
「什么都不做、也什么都不说」**的分支：

| 分支 | 有没有反馈 |
|---|---|
| 改名 | ✅ WARNING，写明滚动发布风险 |
| `expand_only` 违规 | ✅ 报错并列出具体语句 |
| 字段号复用 | ✅ 报错并提示 `reserved` |
| **收窄被抑制** | ❌ **一声不吭** |

### 改法

新增 `narrowing_suppressed()` / `narrowingSuppressed()`——专门区分
「挡下了一次收窄」和「两边本来就一样」，只有前者打日志：

```
table player: 列 port 线上是 bigint unsigned、proto 要 int unsigned NOT NULL DEFAULT 0
——**保持线上的不动**。收窄会丢数据，且在滚动发布期间会被新旧副本来回改。
确实要收窄请人工写 ALTER。
```

**零 SQL 变化**，纯粹是把一个静默行为变成可见行为。

## 附：四条小的

### 不支持的类型静默落 `TEXT`

`sint32` / `sint64` / `fixed32` / `fixed64` / `sfixed32` / `sfixed64`
原先会静默回落成 `TEXT`：建表一路成功，跑到**第一次写入**才抛异常，
而那时列已经建出来了、可能还上了线。

**改法**：建表/生成 DDL 时就 fail-fast。改用 `int32/int64/uint32/uint64` 即可，
取值范围完全一样，只是 protobuf 线上编码不同。

> 注意这里刻意选了 fail-fast 而不是"补上这六个类型的映射"：
> 存量的 `TEXT` 列改成 `int/bigint` 是**跨族**变更，会产出 MODIFY 把数据吃成 0。

### 表名默认值陷阱

没声明 `table_name` 选项时，表名退化成 proto 的 **full name（含 package）**。
把 package 从 `game.v1` 改成 `game.v2`，表名跟着变 → 建出一张**全新的空表**，
旧数据留在旧表里，**两边都不报错**。

**改法**：同步结构时打告警。（`register_all_tables` 本来就强制要求这个选项。）

### `--drop` 的警告不跟着文件走

`proto2sql --drop` 会在每条 `CREATE TABLE` 前加 `DROP TABLE IF EXISTS`。
原先警告只写在 CLI 帮助和文档里——但真正的风险是**生成出来的 `.sql` 文件被别人拿去执行**：
它看起来就是一份普通的建表脚本，`mysql < schema.sql` 一敲，整库蒸发。

**改法**：警告写进生成物的**文件头**，谁打开都能第一眼看见。

### TEXT 索引缺前缀长度，DDL 根本执行不了

MySQL 不允许对 TEXT/BLOB 列建不带前缀长度的索引（`Error 1170`），
而本库把 `string` 映射成 `MEDIUMTEXT`。所以只要在 string 列上声明了
`index` / `unique_key`，产出的就是一条 **MySQL 会直接拒绝执行的 DDL**。

这个洞长期没暴露，是因为**测试只比对 SQL 字符串、从不真的执行**——
拿仓库自带的 `account.proto` 生成建表语句打到 MySQL 8.4 上就是 Error 1170。

**改法**：自动补 `(191)`（utf8mb4 下的经典安全值）。
两个实现现在都补，逐字节一致也随之恢复。

## 三条被证伪的担忧（不用再查）

审查过程中提出过、但**实测证伪**的三条，记在这里免得重复排查：

1. **「回滚会丢数据」** —— 不成立。库**永不 DROP COLUMN**：
   .proto 里删掉字段，线上那列原封不动留着（变成孤儿列）。
   实测 `build_alter_clauses(线上是新结构)` 返回空。

2. **「MEDIUMTEXT/BLOB 不能有 DEFAULT，旧版本 INSERT 会报 Error 1364」** —— 不成立。
   库根本不给 TEXT/BLOB/DATETIME 生成 DEFAULT，它们是**可空列**；
   凡带 `NOT NULL` 的一律带 `DEFAULT 0`。

3. **「字段号对齐依赖列顺序，中间插字段会错位」** —— 不成立。
   对齐全走按列名索引的字典，元数据存在**列注释 `COMMENT 'pb:N'`** 里。
   实测中间插字段仍只产出 `ADD COLUMN`。
